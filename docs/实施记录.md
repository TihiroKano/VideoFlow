## 2. 环境决策与踩坑记录

本机约束：C 盘仅剩 5.1 GB、D 盘 32.8 GB、内存 7.8 GB、无 Rust/编译器。

| # | 问题 | 根因 | 解法 |
|---|---|---|---|
| 1 | 无法使用 Tauri 官方推荐的 MSVC | 未安装 VS Build Tools，安装需 3–6 GB 且主要落在只剩 5.1 GB 的 C 盘 | 改用 **GNU 工具链**：MinGW-w64 (WinLibs POSIX/UCRT) + `stable-x86_64-pc-windows-gnu` |
| 2 | MinGW 解压静默失败并删除了压缩包 | PowerShell 5.1 未加载 `System.IO.Compression.FileSystem`，`[ZipFile]::ExtractToDirectory` 抛错但脚本继续执行 | 解压前 `Add-Type -AssemblyName System.IO.Compression.FileSystem` |
| 3 | `rustup toolchain install` 报 `missing manifest` | 首次安装被中断，toolchain 目录处于半成品状态，重装时报目录非空 | 彻底删除 `rustup\toolchains`、`tmp`、`downloads` 后 `--force` 重装 |
| 4 | `error: could not rename ... 目录不是空的` | 同上，残留文件与新版冲突 | 同上 |
| 5 | `error: linker gcc.exe not found` | 构建启动时 MinGW 尚在下载 | 等 MinGW 就绪后再构建 |
| 6 | `error calling dlltool 'dlltool.exe': program not found` | cargo 通过 PATH 查找 `dlltool`，而 `.cargo/config.toml` 只配了 `linker`/`ar` | 构建时把 `mingw64\bin` 加入 PATH；`scripts/env.ps1` 统一处理，`scripts/dev.ps1` 会校验四个必需工具 |
| 7 | `STATUS_STACK_BUFFER_OVERRUN (0xc0000409)`，rustc 崩溃 | 内存仅 7.8 GB、可用 2 GB，`debug = 2` 下多并行 rustc 爆内存 | `[profile.dev] debug = 0` + `cargo build -j 2` |

> 结论：在低内存机器上做 Tauri 开发，关闭 dev profile 的调试信息是必要项，不是优化项。

## 4. 已实现功能

### 4.1 下载链路（真实可用）

- **URL 校验**：前端 scheme/长度校验 + 主进程 SSRF 防护（私网、回环、链路本地、CGNAT、DNS 重校验）。
- **Provider 解析**：
  - 直链（`.mp4/.m4a/.webm` 等）→ HEAD/Range 探测，无 Range 时退回 `bytes=0-0`，返回真实大小与容器。
  - 站点（Bilibili/YouTube 等）→ `yt-dlp --dump-single-json`，标准化为 `ResolvedMedia`，解析 TTL 15 分钟。
- **双引擎下载**：
  - 原生 HTTP 引擎：8 MiB 分段并发、`.part` + `.resume.json` 原子检查点、ETag/Last-Modified 校验、指数退避、429 尊重 `Retry-After`、长度校验、原子 rename、`name (1).ext` 冲突策略。
  - yt-dlp 引擎：`--progress-template` 机器可读进度、`--concurrent-fragments`、`--merge-output-format mp4`。
- **调度**：并发 1–6（默认 3）、优先级排序、幂等命令、暂停/恢复/取消/重试。
- **FFmpeg**：仅在需要时做无损 remux / 音视频合并，失败保留源分片。

### 4.2 界面

- 三栏骨架、自绘标题栏（最小化/最大化/关闭）、顶部模式分段控件、左导航（首页/下载记录/转换记录/背景/设置）。
- 下载工作台：URL 胶囊、解析结果卡（封面/标题/时长/分辨率/大小/来源）、三项规格选择、开始下载。
- 下载队列：全局速度、剩余任务、全局暂停、逐任务进度/速度/ETA/动作。
- 记录页：搜索、打开、定位、删除（移入回收站，二次确认）。
- 设置页：下载目录、并发、渲染档位（自动/质量/平衡/性能）、玻璃强度、减少动效、高对比度、渲染诊断。
- 背景控制台：上传 JPG/PNG/WebP、适配方式、透明度、模糊、亮度、恢复默认。

### 4.3 Liquid Glass 渲染

- 全局唯一 WebGL2 Canvas，Scissor 分区逐面板绘制；父面板先画、子控件后画（按 DOM 文档顺序排序，不依赖注册先后）。
- 着色器：圆角矩形 SDF + quintic 倒角高度场 + 双界面折射（IOR 1.46）+ 三路采样 + GGX/Smith/Schlick 光边；质量档额外开启边缘 RGB 色散。
- 三档：L1 完整管线 / L2 关闭色散 / L3 纯 CSS 毛玻璃（不支持 `backdrop-filter` 时退化为实色 + 描边 + 阴影），L3 绝不初始化 WebGL。
- 设备探测：WebGL2 能力、`EXT_color_buffer_float`、CPU 核心、`deviceMemory`、120 帧 rAF 微基准 p95；给出可解释推荐理由，用户手选永久优先。

## 5. 与项目书的偏差（已记录的决策）

| 编号 | 项目书要求 | 实施 | 原因 |
|---|---|---|---|
| ADR-001 | Tauri 使用 MSVC 工具链 | 使用 GNU 工具链 + MinGW-w64 | C 盘剩余空间不足以安装 VS Build Tools |
| ADR-002 | `apps/` + `crates/` monorepo | Tauri 标准布局 `src/` + `src-tauri/`，模块名与项目书一致 | 单应用无需多 crate 编译隔离，可显著降低 GNU 工具链下的排错成本 |
| ADR-003 | Three.js 承载 WebGL2 | 原生 WebGL2 | 该管线是屏幕空间后处理，不需要场景图；同样满足「全局唯一 canvas + Scissor」硬约束 |
| ADR-004 | TanStack Query 管理缓存 | 仅用 Zustand | 后端状态由事件总线推送，Query 的缓存失效模型在此无收益 |
| ADR-005 | SQLite 持久化 | 前端设置用 localStorage；主进程设置用 `D:\VideoFlow\settings.json` | 测试开发版优先保证可运行与可清理，避免引入 SQLx 的编译与迁移成本 |
| ADR-006 | 右侧背景控制台常驻 | 背景控制台作为独立页面（左导航「背景」） | 与预览图一致：预览图右侧没有独立面板，是背景图本身 |
| ADR-007 | 支持批量导入 URL | 本期仅单条解析 | 避免交付半成品批量 UI；主进程 `resolve_urls` 已支持一次 50 条，接入成本低 |
| ADR-008 | L3 用预模糊副本 | L3 用 `backdrop-filter`，不支持时退化为实色 | 本应用窗口不透明、背景在 DOM 内，`backdrop-filter` 可靠且画质更好；项目书该约束针对透明窗口场景 |

## 6. 已知限制

1. **格式转换未实现**：只交付 UI，点击「开始转换」会明确提示功能开发中。
2. **`bin/` 中的 sidecar 需随项目分发**：yt-dlp 承担站点解析；缺失时站点链接会返回 `PROVIDER_TOOL_MISSING`，直链下载不受影响。
3. **yt-dlp 为外部程序**：站点风控、需登录或受 DRM 保护的资源会返回明确分类错误，不做任何绕过。
4. **应用重启后的自动续传未接线**：检查点已落盘，但启动时未扫描 `.resume.json` 自动恢复队列（暂停/恢复在本次会话内完整可用）。
5. **不含数字签名与自动更新**：测试开发版不打包、不签名。
6. **HLS 任务不支持断点续传**：分片由 FFmpeg 单次拉完，取消后需从头再下
   （原生 HTTP 引擎的直链下载仍有断点续传）。
7. **Browser Resolver 当前只覆盖抖音**：架构是通用的（`ProviderKind::Browser`
   按域名注册），但注入脚本里的字段映射是按抖音的 `aweme_detail` 写的；
   接入新站点需要在 `hook.js` 与 `browser/mod.rs` 里补该站点的提取规则。
8. **抖音需登录才能看的视频**：解析窗口用独立持久 profile，可在其中登录一次；
   本轮未做登录引导 UI。

## 8. 开发过程中修复的缺陷

以下是实现期间发现并修复的真实缺陷，按发现顺序记录。

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 1 | WebGL 玻璃完全不出图，`compileShader` 报 `CONTEXT_LOST_WEBGL` 且驱动日志为空 | React 19 StrictMode 双次挂载：第一次卸载时调用了 `WEBGL_lose_context.loseContext()`，而 `getContext` 对同一 canvas 元素只返回同一个上下文对象，第二次挂载拿到的是已丢失的上下文 | 卸载时不再主动丢失上下文，改为逐个释放 texture/buffer/VAO/program；并在初始化时用 `isContextLost()` 兜底，同时监听 `webglcontextlost` 事件 |
| 2 | 背景与玻璃错位，面板边缘出现水平接缝 | 背景着色器直接用 `vUv`（原点在左下），玻璃着色器用翻转后的 `luv`（原点在左上），两者坐标系不一致，背景被上下翻转 | 背景着色器同样翻转为左上原点 |
| 3 | 面板位置错乱/残留上一帧 | 只在 canvas 尺寸变化时重绘；内容变化（空状态 ↔ 解析结果）会改变面板高度而画布尺寸不变 | 为每个已注册面板加 ResizeObserver；新增 `notifyGlassRedraw()` 供页面切换时显式请求重绘 |
| 4 | 队列只显示 2 条任务，已完成任务消失 | `TaskQueuePanel` 过滤掉了终态任务，而预览图中队列包含一条「已完成」 | 队列改为展示最近 6 条（含刚完成的），历史记录仍在「下载记录」 |

## 11. 第二轮缺陷修复（2026-09-19）

用户对照运行中的界面提出 8 项问题，逐项定位并修复。

### 11.1 圆角：可见直角（根因在着色器坐标系）

**现象**：同一块玻璃面板，部分角是圆角、部分角是直角；用户要求「每个角都检查」。

**根因**：`GLASS_FRAG` 里 SDF 用的是**整块画布**的归一化坐标：

```glsl
vec2 p = (luv - 0.5) * sizePx;     // luv 是全画布 uv，不是面板内的 uv
```

`uRect` 只用来做 Scissor 裁剪，没有参与坐标换算，于是圆角矩形实际被摆在「以画布中心
为原点、尺寸等于面板」的位置。落到面板范围内的只是那个矩形的一个窗口——距离画布中心
越远越靠外，`sdRoundBox` 的返回值越正，`mask` 越小直到被 `discard`。

实测一组数（画布 1295×889，左栏面板 rect ≈ (22,22,200.7,809)，圆角 22）：
面板左上角 `d ≈ -3.7`（勉强有圆角），右上角 `d ≈ -21.9`（远在内部，**完全直角**）。

**修复**：先用 `uRect` 把画布坐标换算成面板局部坐标，再算 SDF：

```glsl
vec2 canvasPx = luv * uResolution;
vec2 p = canvasPx - uRect.xy - sizePx * 0.5;
```

顺带修正了 `fragPx`（背景采样位置）——它此前同样用了错误的换算，
导致玻璃内采到的背景区域与面板位置有偏移。

### 11.2 删除开发期诊断徽标，统一底部高度

- 移除界面左下角的 `tier=… bg=… host=… glass=…` 黑条，连同 `AppShell` 里的诊断
  定时器、`onUnavailableReason` 回调与 `.vf-diag-badge` 样式一并删除（避免留下死代码）。
- 左栏底边比中央主区高 18px（`--vf-sidebar-bottom-extra`），底部出现高矮不齐的两个圆角。
  删除该变量，左栏与主区同用 `--vf-bottom-center`，底边对齐。

### 11.3 URL 输入框外层多余的框（第一轮判断有误，此处订正）

第一轮把「输入框外多出一圈框」归因于 11.1 的玻璃错位，改动后用户复测**仍然复现**，
且现象只发生在**点击输入框之后**。改用浏览器实测（Vite 开发服务器 + 真实点击 +
`getComputedStyle`）后定位到真正原因：

全局规则 `base.css: :focus-visible` 对**所有**元素无差别加焦点描边：

```css
:focus-visible { box-shadow: var(--vf-focus); border-radius: var(--vf-radius-control); }
```

鼠标点击文本输入框同样会命中 `:focus-visible`，于是内层那个裸 `<input>` 自己也被画了
一道 3px 描边：

```
input.vf-composer__input  rect x=190 y=106 w=178 h=54
  box-shadow: rgba(143,184,255,.66) 0px 0px 0px 3px
```

它的上、下与外层胶囊齐边，左内缩 50px（让过链接图标）、右内缩 18px，看上去就是
「胶囊内部多出一个方框」；再加上全局规则把它的圆角改成 14px，方框感更强。

**修复**：

- 组合控件（玻璃胶囊 + 内层裸输入框）的焦点反馈一律由外层容器负责，
  内层输入框逐项还原全局规则强加的样式：

  ```css
  .vf-composer__input:focus-visible,
  .vf-library__search-input:focus-visible { box-shadow: none; border-radius: 0; }
  ```

- 「下载记录」的搜索框是同一种结构，一并处理，并给 `.vf-library__search:focus-within`
  补上焦点环（否则屏蔽后就没有焦点可见性了）。

**顺带修好的死代码**：`.vf-composer__field` 上的 `data-state` 从未到达 DOM ——
`GlassSurface` 只透传 `className / id / role / aria-label` 和 `data-glass-*`，
所以 `.vf-composer__field[data-state="focus"|"invalid"]` 两条规则一直不命中，
**非法链接时本该出现的红色描边是失效的**。改用类名（`is-focus` / `is-invalid`）后
焦点环与红色校验环都能正常显示。

验证（浏览器实测）：聚焦后 `input.boxShadow === "none"`、外层 `field.boxShadow` 为
3px 浅蓝环；Tab 键盘走到输入框仍有焦点环；输入 `http://example.com/a.mp4` 后胶囊变为
`is-invalid` 且描边为 `--vf-danger` 系红色；搜索框同样无内层方框、外层胶囊有环。

### 11.5 下载卡顿（三处真实缺陷）

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 1 | yt-dlp 下载时界面进度长期不动 | `tokio::select!` 把 `lines.next_line()` 与 400ms 的暂停轮询放在一起竞争。sleep 抢先时 `next_line` 的 future 被丢弃，而它已读进缓冲区、尚未遇到换行的字节一并丢失，进度行残缺或消失 | stdout 交给独立任务读取并通过 channel 回传，`select!` 只等 channel，不丢数据 |
| 2 | 进度条中途倒退/看起来像重来 | `-f video+audio` 是两段串行下载，yt-dlp 的第二段 `downloaded_bytes` 从 0 重新计数 | 进度模板加入 `%(info.format_id)s` 识别换流，把上一段总量累加为基数；总量只增不减 |
| 3 | 长任务偶发整体冻结 | stderr 读取在 16 KB 处 `break`，管道缓冲区写满后子进程阻塞在写 stderr 上 | 改为一直读到 EOF，只截断保留的文本 |

另外把原生 HTTP 引擎的单分片重试上限从 3 次提到 6 次（退避 1/2/4/8/8/8 秒），
弱网下不再因为几次瞬时抖动让整个任务失败。

### 11.6 「在文件夹中显示」跳到错误目录

**根因**：`Command::arg` 在参数含空格时会把**整个参数**包进引号，于是 explorer 收到的是

```
"/select,C:\...\My Videos\a b.mp4"      ← /select, 被包在引号里，开关失效
```

explorer 认不出 `/select` 开关，就退化成打开默认文件夹。实测对比（子进程打印
Win32 原始命令行）：

```
[旧 arg/有空格] "/select,C:\Users\me\My Videos\a b.mp4"      ← 坏
[旧 arg/无空格] /select,C:\VideoFlow\Downloads\a.mp4          ← 侥幸能用
[新 raw_arg]    /select,"C:\Users\me\My Videos\a b.mp4"       ← 正确
```

**修复**：改用 `CommandExt::raw_arg`，只给路径加引号：`raw_arg(format!("/select,\"{path}\""))`。
下载文件名常带空格（标题里的空格、冲突策略追加的 `name (1).mp4`），所以这个 bug 很容易触发。

### 11.7 抖音无法下载 / Bilibili 无法下载 1080P

两者是**同一个根因**：站点侧的登录态要求。

- **抖音**：yt-dlp 的 Douyin 提取器需要新鲜 Cookie 才能拿到播放地址，匿名请求必然失败。
- **Bilibili**：实测 `yt-dlp -F` 输出明确提示
  `Format(s) 1080P 60帧 are missing; you have to become a premium member…Use --cookies-from-browser or --cookies`
  ——1080P 60 帧 / 1080P+ 只对已登录账号开放（普通 1080P 匿名可下，已实测 1080p 的
  H.264 / H.265 / AV1 三种编码都能成功合并）。

**修复**：新增「设置 → 下载 → 登录状态」，支持两条通路：

| 取值 | 行为 | 取舍 |
|---|---|---|
| `browser:edge|chrome|firefox` | `--cookies-from-browser` | 省事，但 Chromium 系浏览器运行时会锁住 Cookie 数据库，yt-dlp 复制不出来（上游 issue #7271），必须完全退出浏览器 |

同时把 `classify_stderr` / `classify_failure` 里的登录态错误单独归类为
`PROVIDER_NEEDS_COOKIES`，并给出可执行的提示，不再被压成笼统的「不支持」。

> 合规边界：这里使用的是用户本人在浏览器里已有的登录状态，取到的仍是该账号本来
> 就有权观看的内容，不涉及绕过任何访问控制（项目书 §0.2）。

### 11.8 Bilibili 清晰度标签与编码偏好

## 12. 第三轮缺陷修复（2026-09-19）

用户报告：加入队列后封面丢失、任务默认停在「等待开始」需手动点、进度卡死后要点一次
暂停才显示已完成。

### 12.1 封面丢失：站点图床的防盗链

**现象**：任务卡的缩略图位置显示浏览器的破图图标；预览卡同样取不到封面（它的
`onError` 把 `<img>` 藏了，所以只表现为没有图）。

**根因**：Bilibili 的图床（`i2.hdslb.com`）按 Referer 做防盗链。实测：

| Referer | 结果 |
|---|---|
| 无 | 200 |
| `http://localhost:1420/`（开发态页面源） | **403** |
| `https://www.bilibili.com/` | 200 |
| `tauri://localhost/`（打包后页面源） | **403** |

WebView 加载 `<img>` 时会带上页面自身的 Referer，于是**在应用里永远取不到封面**。

**修复**：

- 两个 `<img>` 都加 `referrerPolicy="no-referrer"`——B 站图床在无 Referer 时正常返回；
- 解析结果里的封面地址统一从 `http://` 升到 `https://`（该 CDN 两种协议都支持），
  避免将来页面源变成安全上下文后被混合内容策略拦掉；
- 任务卡的 `<img>` 补上 `onError` 退回色块（此前只有预览卡有，所以只有它不露破图）。

浏览器实测：同一个 URL，未命中缓存时默认策略 `onerror` + `naturalWidth=0`
（网络层为 `net::ERR_BLOCKED_BY_ORB`，即 403 响应体不是合法图片被拦），
带 `no-referrer` 则正常加载（1076×608）。注意同一 URL 成功后会被 HTTP 缓存，
后续用默认策略请求也会「成功」，验证时必须用查询参数打散缓存。

### 12.2 任务默认停在「等待开始」

**根因**是命令返回值与事件之间的竞态。`create_task` 的写法是：

```rust
state.insert_task(task.clone());   // 状态 = queued
state.emit_task_updated(&task);
state.wake();
state.pump();                      // 可能立刻推进到 downloading 并发出事件
Ok(task)                           // ← 返回的却仍是上面那份 queued 快照
```

前端拿到返回值后会 `upsert` 一次。若 `pump` 已经把任务推进到 downloading 并发出
`task.updated`，这个 queued 快照就会**把刚收到的新状态覆盖回去**，界面停在
「等待中 / 立即开始」；用户点一次按钮之所以能恢复，是因为那次命令返回的是最新状态。

**修复**：`create_task` / `resume` / `retry` 一律在 `pump()` 之后重新读取当前状态再返回。

### 12.3 进度卡死、点一次暂停才显示完成

两处叠加：

1. **进度记录不会随终态清理**。前端卡片取值的优先级是
   `progress?.downloadedBytes ?? task.downloadedBytes`，而进度记录是 4 次/秒节流写入的，
   会停在下载中途的百分比。任务完成后卡片虽然显示「已完成」，进度条却仍停在半途。
   修复：`upsert` / `replaceAll` 在任务进入终态时清掉它的进度记录。

2. **任何一次状态事件丢失都会让界面永久停在旧状态**。项目书 §4.2 写明「后端是状态
   真相源，前端只做乐观展示」，但此前的实现只有事件这一条通路，事件丢了就没有兜底，
   表现正是「不点一下按钮就不更新」（因为命令返回值恰好是最新状态）。
   修复：新增低频对账 `useTaskReconcile`——每 2 秒比对

## 13. 第四轮修复（2026-09-19）

用户复查：进度条仍会卡死、需要对账式的「点了暂停才更新」；另提三项新增需求。

### 13.1 进度条卡死（第三轮判断不完整，此处补上根因）

第三轮加了对账兜底，但**签名里没有 `downloadedBytes`**，所以对账只能修状态、修不了进度，
用户复测仍复现。真正的结构性问题在数据源上：

卡片的取值是

```ts
const downloaded = progress?.downloadedBytes ?? task.downloadedBytes;
```

即**优先读一份独立的 `progress` 记录**（由 `task.progress` 事件节流写入），
只有它不存在时才读任务对象本身。于是只要进度事件流中断一次，
那份记录就会永久停在中断时的百分比，而任务对象里更新的字节数被完全忽略——
用户点一下暂停之所以能恢复，是因为那次命令返回的**任务对象**才是新的。

**修复**：取消双数据源，进度只写回任务对象，卡片也只从任务读：

- `taskStore.applyProgress` 改为只 merge 进 `tasks`，删除 `progress` 记录与 `progressFor`；
- `taskSignature` 纳入 `downloadedBytes`，对账同时覆盖进度；

## 14. 第五轮修复（2026-09-19）

用户反馈：`start.cmd` 报错（希望改为直接运行 exe）；下载已正常；更换背景时提示无法访问文件管理器。

### 14.1 更换背景失败：缺少 capabilities 声明

**根因**：`src-tauri/capabilities/` 目录**不存在**。

Tauri 2 的权限模型里，**应用自定义命令无需授权**（`invoke_handler` 注册即可调用），
但**插件命令必须通过 capability 显式放开**。这个项目一个 capability 文件都没有，
于是 `@tauri-apps/plugin-dialog` 的 `open()` 被拒绝——而其它功能（解析、下载、事件）
全部正常，正好符合「只有文件选择器用不了」的表现。

**修复**：新增 `src-tauri/capabilities/default.json`：

```json
{
  "identifier": "default",
  "windows": ["main"],
  "permissions": ["core:default", "dialog:default", "dialog:allow-open"]
}
```

已核对 `tauri-plugin-dialog 2.7.3` 的权限清单：`default` 集合本就包含
`allow-message`、`allow-save`、`allow-open`，`dialog:allow-open` 也单独存在，
两者都有效。

### 14.2 启动器报错 101：编译缓存残缺 + 内存不足

`start.cmd` 退出码 101，cargo 报：

```
error: only metadata stub found for `rlib` dependency `core`
       please provide path to the corresponding .rmeta file with full metadata
```

这是**只产出过 metadata 的残缺 rlib**（`cargo check` 或中途被中断的构建留下的
`.rmeta` 存根）被当成可链接产物使用。此前调试期间多次强制结束过 cargo/rustc 进程，
留下了这类残留。修复：`cargo clean`（清掉 4.2 GB 目标目录）后重新构建。

顺带记一条环境约束：本机总内存 7.83 GB，而 Trae CN + Edge + 微信等常驻进程已占用
约 7.1 GB，**可用内存常年只有 0.7 GB 上下**。并行 rustc 在这种余量下极易以
`STATUS_STACK_BUFFER_OVERRUN (0xc0000409)` 崩溃（§2 第 7 条同一现象），
因此这台机器上的构建必须用 `-j 1`。

### 14.3 独立 exe：不再依赖命令行

用户要求「直接变成 exe 的启动文件」。原来的 `start.cmd` 是**开发入口**：它要起
Vite 开发服务器、调 cargo 编译、依赖 PowerShell 执行策略绕过（见 §1 与 §11.6），
任何一环出问题都会启动失败。

改用 Tauri 的构建模式产出**自包含可执行文件**：

```
node node_modules/@tauri-apps/cli/tauri.js build --debug --no-bundle
```

构建模式会把 `dist/` 内嵌进可执行文件（不再使用 `devUrl`），因此产物不需要
开发服务器、不需要 npm、不需要 PowerShell，双击即可运行。`--no-bundle` 跳过
NSIS 安装包（用户不需要安装包）。

产物复制到项目根目录 `VideoFlow.exe`。放在这里也是刻意的：`sidecar` 的工具查找
顺序里第一条是「可执行文件同级的 `bin/`」（`src-tauri/src/platform/sidecar.rs`），
所以 `D:\mihoyo\VideoFlow\bin\{yt-dlp,ffmpeg}.exe` 依然能被找到。

**必须随 exe 一起提供的 `WebView2Loader.dll`。** 第一次直接双击 exe 是**静默退出**，
退出码 `0xC0000135`（STATUS_DLL_NOT_FOUND）。用 `objdump -p` 看导入表才定位到：

- MinGW 的 `libgcc_s_seh-1` / `libstdc++-6` / `libwinpthread-1` **没有**出现在导入表里
  （已经是静态链接，不是它们的问题）；
- 真正缺的是 **`WebView2Loader.dll`** —— GNU 工具链下 Tauri 是动态链接它的。

开发态之所以没暴露这个问题：`scripts/dev.ps1` 会把 `mingw64\bin` 加进 PATH，
而且 `cargo` 在构建后会自动把 `WebView2Loader.dll` 复制到 `target\debug\`，
`cargo run` 正好从那里启动。双击 exe 两者都没有，于是失败。

DLL 取自 `webview2-com-sys-0.38.2\x64\WebView2Loader.dll`（156 KB），
与 `VideoFlow.exe` 同级放置。补上之后启动耗时 **0.5 秒**（对比开发态要先起 Vite、
再等 cargo 编译）。

`start.cmd` 保留，作为需要热更新的开发入口；日常使用直接双击 `VideoFlow.exe`。

## 16. 持久化队列：重启不再丢任务（2026-09-19）

§15 之后用户选择继续补齐 §3.2 里缺口最大的一项：**Scheduler 维护持久化队列；应用关闭时
运行中任务安全落盘为 `paused`；下次启动校验临时文件和 ETag/Last-Modified 后恢复。**
此前任务只存在内存里，重启即清空。

### 16.1 快照文件

`D:\VideoFlow\tasks.json`（与 `settings.json` 同级，不写 C 盘），结构：

```json
{ "version": 1, "savedAt": "...", "tasks": [ /* PersistedTask */ ] }
```

`PersistedTask` = `DownloadTask`（`#[serde(flatten)]`）+ `streamUrl` / `audioUrl` / `scratchDir`
三个外壳字段。**为什么要有这层壳**：下载地址在 `DownloadTask` 里是 `#[serde(skip)]` 的
（不能下发给前端），但恢复队列必须带上它们，否则重启后没法继续下载。

写入是原子的：先写 `tasks.json.tmp` 再 `rename`，中途被杀不会留下半个 JSON；
读取时文件缺失或损坏都只返回空列表并打日志，不阻塞启动。

### 16.2 落盘时机

- **节流写盘**：`mutate` / `insert_task` / `remove_task` / 调度取出任务时打 `dirty` 标记，
  后台每 2 秒检查一次，有变更就合并写一次（不随进度事件写盘，避免每秒几十次 I/O）。
- **退出前再写一次**：`RunEvent::ExitRequested` 时调用 `persist_snapshot()`，
  保证「关窗口」这一下也落盘。

### 16.3 运行中 → paused 的两个位置

`TaskStatus::requires_pause_on_restore()` 判定 `downloading / verifying / merging / pausing`，
**写盘时**和**恢复时**各降级一次：前者保证快照语义正确（这份进程结束后它们没有运行实体），
后者是硬退出（任务管理器结束进程、断电）的安全网——那种情况下快照里仍是 `downloading`。

### 16.4 恢复流程

`AppState::new` 里（窗口加载「快照」之前）读回记录 → 降级状态 → 把外壳里的下载地址、
临时目录装回任务 → `version += 1`（前端不会把恢复出来的任务当成旧快照）。
启动 800ms 后（等前端订阅完成）执行一次 `pump()`，让恢复出来的排队任务继续跑。

「校验临时文件和 ETag/Last-Modified」由既有机制完成：原生引擎在 `run_native` 里
**优先读磁盘上的检查点**（`http::load_checkpoint`，由每个分片完成时原子更新，
比内存快照新），拿到后照旧对比 ETag/Last-Modified，不一致就从头下；用户手动点「继续」
时还会先走「校验中」并检查临时分片是否还在。

## 17. 第七轮：卡顿实测与 sidecar 探测缓存（2026-09-19）

用户反馈「从设置切到背景会出现 2-3 秒卡顿」。这一轮**先量化再改代码**：用 WebView2 的远程
调试端口把真实应用接上 CDP（`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`），
在应用内直接测点击到出帧、帧间隔、主线程长任务与 IPC 往返。诊断脚本留在
`test/_analysis/cdp.mjs`（临时工具，随 test 目录可整体删除）。

### 17.1 实测数据（真实应用，不是浏览器预览）

| 场景 | 指标 | 结果 |
|---|---|---|
| 设置 → 背景（应用已运行一段时间） | 点击到出帧 | **13–34 ms** |
| 设置 → 背景（冷启动后首次） | 点击到出帧 | 152–231 ms；主线程长任务 77–201 ms |
| 背景页滑块连续拖动 40 次 | 总耗时 | 199 ms（每个事件约 5 ms） |
| 背景快照写入 localStorage（291 KB） | 单次 | 2.8 ms |
| 有下载在跑时切换页面 | 帧空档 | 一次出现 133/417 ms，另一次为 0 |
| 有下载在跑时 IPC 往返 | 单次 | 2.4–8.9 ms |
| **每次进设置页重跑的 sidecar 探测** | 一次调用 | **2.3–3.0 秒**（拉起 yt-dlp + ffmpeg 两个进程） |

页面切换本身很快、主线程没有被阻塞；偶发的几百毫秒空档与「有下载在跑 + 本机可用内存
常年 0.6–0.7 GB」相关，不是某一段代码固定阻塞。

### 17.2 修复：sidecar 探测一次会话只做一次

查到的实打实的浪费是：**每次进入设置页都会重新把 yt-dlp.exe 与 ffmpeg.exe 拉起来取版本**
（本机 2.3–3.0 秒，两个大进程的启动/退出抢 CPU 与磁盘），而用户报告的路径正好是
「设置 → 背景」。改法：

- `sidecar_status` 改为 `async` + `spawn_blocking`（`commands/mod.rs`），任何情况下
  不占用 UI 相关线程；`ToolStatus::missing()` 提为 `pub` 供失败兜底。
- 探测结果存进 `settingsStore.sidecar`，**一次会话只探测一次**，再次进设置页直接复用
  （工具就在磁盘上，会话期间不会变）。
- 诊断区在首次探测未完成时显示「检测中…」，不再提前显示「未找到」。

### 17.3 一个必须记录的坑：CDP 打桩实验是无效的

排查过程中做过一次「把 `sidecar_status` 打桩再对比卡顿」的对照实验，结论自相矛盾。
后来查到根因：`window.__TAURI_INTERNALS__` 及其 `invoke` 都是
**`writable: false, configurable: false`**，赋值静默失败——所谓「打桩」根本没生效，
A/B 两组跑的都是真实探测。以后要在页面里拦截 IPC，只能从应用代码侧留开关，
不能在页面里改。

## 18. 第八轮：窗口四角没有被壁纸填满（2026-09-19）

用户反馈「边缘地区的壁纸填充需要填满才行」，附的是窗口右上角那一片纯色截图。

### 18.1 根因

- `tauri.conf.json` 里窗口是 **`"transparent": false`**：一个不透明的方形窗口。
- 而根节点 `.vf-window` 用 `border-radius: var(--vf-radius-shell)`（28px）+
  `overflow: hidden` 裁剪了它内部的**所有背景层**（壁纸层与玻璃画布都在里面）。
- 于是 28px 圆角之外那一圈露出的其实是 **`body` 的深蓝底色 `#062f57`**——
  观感就是「四角没有被壁纸填满」。

像素采样（右上角，修复前）：角内 12px = `6,47,87`（正是 `--vf-bg-deep`），
30px 才是壁纸色 `34,75,121`。用户截图里那道弧线就是这条裁剪边界。

### 18.2 修复

`src/design/base.css`：根节点去掉圆角、保持方形，让壁纸与玻璃画布铺满整个窗口矩形；
圆角只由内部面板与控件自己负责（它们本来就是圆角）。`--vf-radius-shell` 令牌保留但不再使用。

修复后采样：右上角角内 12px = `33,75,120`（壁纸色），左上/左下/右下同样铺满；
整窗截图确认侧边栏、面板、模式切换等布局与观感无变化。

### 18.3 与预览图的一处偏差（记录）

`docs/预览图.png` 画的是**圆角窗口**。在「不透明方形窗口」的前提下，根节点一旦裁圆角，
四角必然露出底色而不可能被壁纸填满——两者不可兼得。本轮按用户要求选择**方形铺满**。

若之后想要真圆角窗口（四角透出桌面而不是壁纸），做法是把 `transparent` 改成 `true`
再保留圆角，但需要重新验证 WebView2 在透明窗口下的合成与性能（本项目早期在透明遮罩上
踩过坑，见 §11）。

## 19. 第九轮：补齐 §3 方案书最后三项（2026-09-19）

用户要求把 §3 下载方案书剩下没做的三项一起补完：每域名并发上限、设备低档自动下调并发、
Provider 提供时的 SHA-256 校验。

### 19.1 每域名并发上限（§3.2）

§3.2 原文：「同一来源可设置每域名并发上限，避免触发服务端限流」。

- 新设置项 `perHostConcurrency`（默认 2，可调 1–6），设置页新增「同一来源并发上限」滑块。
- 调度器 `take_next_schedulable` 先统计**每个来源正在跑的任务数**，再挑候选：
  该来源已经跑满的任务本轮直接跳过，让其它来源先走；一个都挑不出来时 `pump` 正常收尾，
  等有任务结束再重新调度（`run_task` 结束时会再 `pump` 一次，不会卡死）。
- 来源判定用**页面来源域名**而不是媒体地址（`core::model::task_source_host`）：
  限流按站点算而不是按 CDN 节点算，而且 yt-dlp 任务压根没有单独的媒体地址
  （只有 `137+140` 这类选择器）。域名统一小写并去掉 `www.`。

### 19.2 设备低档自动下调并发（§3.2）

§3.2 原文：「…设备低档或网络受限时自动下调」。

- 前端把设备探测得到的档位（`effectiveTier`）通过 `deviceTier` 设置推给主进程：
  启动同步一次，档位变化（`setProfile` / `setTierChoice`）时再推一次。
- 主进程用 `AppState::limits()` 把用户设置值按档位封顶（`core::model::device_tier_caps`）：

  | 档位 | 同时下载 | 单任务分段 |
  |---|---|---|
  | quality / 未知 | 用户设置（≤6） | 用户设置（≤8） |
  | balanced | ≤3 | ≤3 |
  | performance | ≤2 | ≤2 |

- `pump` 与 `run_native` 都改用 `limits()`，所以同时任务数与分段并发一起受控。
- **未实现**：§3.2 里的「网络受限时自动下调」——需要可靠的网络质量信号，
  目前只在设备档位这一维度下调，已在设置页文案里如实说明。

### 19.3 Provider 提供时的 SHA-256 校验（§3.3）

§3.3 原文：「完成后进行长度校验；Provider 提供时校验 SHA-256」。

- `MediaStream` 新增 `sha256`（十六进制小写）字段；`direct` Provider 从响应头解析：
  RFC 9530 `Content-Digest` / RFC 3230 `Digest`（`sha-256=:BASE64:` 或十六进制）、
  以及 S3 的 `x-amz-checksum-sha256`（base64）。**只在完整 200 响应上取摘要**，
  206 部分响应的摘要是针对那一段的，绝不能拿来校验整文件。
- 任务侧用 `DownloadTask.expected_sha256`（内部字段）携带，随队列快照一起持久化，
  重新解析时按新结果刷新；yt-dlp 流不提供哈希，保持为空（只做长度校验）。
- 下载完成、长度校验之后、**rename 成最终文件之前**校验：不匹配就删除 `.part` 与
  断点文件，返回 `INTEGRITY_ERROR`（§3.5 要求「删除不可信最终产物」）。
  哈希计算跑在 `spawn_blocking` 里，按 1 MiB 分块流式读取。
- 需要音视频合并的任务跳过哈希校验：最终文件是 FFmpeg 重新封装的结果，哈希本来就不适用。

### 19.4 本轮验证

| 项 | 方式 | 结果 |
|---|---|---|
| Rust 单测 | `cargo test --no-default-features --lib -j 1` | **38 通过 / 0 失败**（+5，见下） |
| 前端类型检查 | `node node_modules/typescript/bin/tsc --noEmit` | 通过 |
| 应用构建 | `tauri build --debug --no-bundle -- --jobs 1` | 通过（36 秒），产物已覆盖根目录 `VideoFlow.exe` |

## 20. 第十轮：抖音解析排查与登录态诊断（2026-09-19）

起因：用户提供抖音分享链接 `https://v.douyin.com/AMva9tRuEqU/`（分享文案整段粘贴），
反馈「无法解析下载」。本轮把抖音这条路彻底查清，并顺手修掉两个真实缺陷。

### 20.1 结论：抖音当前无法用纯 HTTP 客户端解析（已实测确认）

排查链路与每一步的实测结果：

| # | 尝试 | 结果 |
|---|---|---|
| 1 | yt-dlp 直连（无 Cookie） | `ERROR: [Douyin] …: Fresh cookies … are needed` |
| 2 | 手机 UA / 百度蜘蛛 UA / 带 Referer | 抖音 PC 页与 `m.` / `iesdouyin` 分享页**都没有服务端渲染的视频数据**，`_ROUTER_DATA` 里只有页面上下文，没有 `play_addr` |
| 3 | 无头 Edge 打开 douyin.com | 命中「验证码中间页」（Argus 滑块），拿不到任何 Cookie |
| 4 | **真实可见 Edge 会话**（独立临时 profile，正常渲染） | 成功写入 36 个 Cookie：`ttwid`、`s_v_web_id`、`__ac_nonce`、`__ac_signature`、`odin_tt`、`x-web-secsdk-uid`、`web_sign_token` … |
| 5 | 用第 4 步的**真实 Cookie** 调 `aweme/v1/web/aweme/detail/` | **仍然 403**：`Blocked by ArgusSecurityPlugin Uifid Not Found` |
| 6 | 补上 `Uifid` 请求头（值取 `x-web-secsdk-uid` / `odin_tt`） | 错误前进一步，变成 **`Blocked by ArgusSecurityPlugin Signature Not Found`** |
| 7 | 浏览器正在运行时读 Edge Cookie 库 | `Could not copy Chrome cookie database`——Chromium 系对 Cookie 库加**独占锁**，`File.Copy` / `CopyFileEx` 均报 `ERROR_SHARING_VIOLATION`，应用侧无法绕过 |

第 6 步是决定性证据：补上 `Uifid` 后错误变成「缺签名」，说明该接口**必须**带上
页面 JS 现算的 `a_bogus` 签名。而签名依赖抖音的 jsvmp 混淆虚拟机与运行环境指纹，
纯 HTTP 客户端（含 yt-dlp）都拿不到。yt-dlp 上游源码里对此的注释就是
`# TODO: Run verification challenge code to generate signature cookies`，
即上游已知未实现。

**所以：这不是本项目配置问题，也不是「没配浏览器登录态」的问题——换上任何
真实登录态都无效。** 该结论已写入 §6 已知限制。

### 20.2 本轮实际修复的两个缺陷

排查过程中暴露了两个与抖音无关、但确实会误导用户的问题：

**(1) 浏览器锁库报错被压成「解析失败」。**
`classify_stderr` 的登录态关键字是 `cookies`，而 yt-dlp 锁库时的原文是
`Could not copy Chrome cookie database`（`cookie` 单数，不含 `cookies`），
于是掉进兜底分支，用户只看到一句「解析失败」+ 一大段英文原文，
完全不知道「关掉浏览器就好」。
现在新增 `PROVIDER_COOKIE_LOCKED`（`error.rs`），并把判定**放在登录态判断之前**
（两者都提到 cookie，混在一起会让人白折腾登录状态），文案直接点名浏览器。

**(2) 分享文案整段粘贴会被判「格式不正确」。**
抖音/快手的分享永远是「口令 + 链接 + 提示语」一整段，用户习惯全选复制，
粘进来的不是纯链接。`urlValidation.ts` 新增 `extractUrl()`：先从文本里摘出
第一条 `https?://` 链接（排除中文字符与全角标点，避免把后面的说明文字吃进去），
再做校验；`UrlComposer` 在提交时把输入框收敛成真正要解析的那条链接。
输入框占位文案同步改成「粘贴视频链接，或整段抖音分享文案」。

### 20.3 顺带补上的登录态诊断

`platform/browser.rs`（新增）：登录态来源解析（`browser:` / `file:` / 空）、
浏览器显示名与进程映像名映射、用 `tasklist` 探测浏览器是否在运行
（`None` = 无法判定，不猜）。`CookieSourceStatus::detect()` 一并检查
cookies.txt 是否还在。

新增 IPC `cookie_source_status`，设置页「登录状态检查」一行据此显示一句
结论：浏览器在跑就黄字提示「需要完全退出」，cookies.txt 丢了就提示重选，
能读就显示「可以读取它的登录状态」，并带「重新检测」按钮（浏览器开关随时会变，
不做缓存）。这条对 Bilibili 高清晰度（确实依赖登录态）是有用的。

### 20.4 本轮验证

| 项 | 方式 | 结果 |
|---|---|---|
| Rust 单测 | `cargo test --no-default-features --lib` | **51 通过 / 0 失败**（+13：yt-dlp 归类 6 项、browser 7 项） |
| 编译（含 GUI） | `cargo check` | 通过（4m26s） |
| 前端类型检查 | `node node_modules/typescript/bin/tsc --noEmit` | 通过 |
| 前端构建 | `node node_modules/vite/bin/vite.js build` | 通过 |

## 21. 第十一轮：Browser Resolver 与 M3U8 Parser（2026-09-19）

按用户确认的目标架构落地三块解析能力，统一向 Native HTTP Engine / FFmpeg 提供标准化媒体资源：

```text
yt-dlp            → 常规站点
Browser Resolver  → 有浏览器验证/动态签名的平台（抖音）
M3U8 Parser       → HLS
        ↓ 统一产出 ResolvedMedia
Native HTTP Engine → 下载        FFmpeg → 合并/封装
```

**硬约束：本轮未新增任何依赖。** 本机离线，`D:\rust\cargo\registry` 只有 321 个 crate，
`tungstenite` / `tokio-tungstenite` / `websocket` / `sha1` / `aes-gcm` 全部缺失——
所以 CDP-over-WebSocket 与「自己实现 AES 解密」这两条路都走不通，方案据此重新设计。

### 21.1 共享改动：referer 传递链

排查中发现引擎层**早就支持 referer**（`http.rs` 72/196/480 行、`ytdlp.rs` 72 行都在消费它），
但上层从未传过：`state.rs` 里两处硬编码 `referer: None`。抖音 CDN 直链在这点上很明确——
带 `Referer: https://www.douyin.com/` 返回 206，不带直接 403，所以这条链必须打通。

- `MediaStream.referer` 与 `DownloadTask.referer`（均 `skip_serializing`，不下发前端）
- `DownloadTask.duration_sec`：HLS 推进度要用（同样 `skip_serializing`）
- 这三个字段都加进了 `PersistedTask` 外壳，否则**重启后恢复的任务会丢 referer 而 403**

### 21.2 Browser Resolver

不碰签名算法，只让页面自己按正常流程请求，我们在旁边把响应捞回来。

- `resolver/browser/mod.rs`（纯逻辑，可脱 GUI 单测）：host 白名单、哨兵地址编解码、
  载荷 → `ResolvedMedia`
- `resolver/browser/hook.js`：改写 `fetch` 与 `XHR`，抓到 `aweme/v1/web/aweme/detail`
  的响应后精简为 `{desc, durationMs, cover, play, ladder}`（`ladder` 按分辨率去重、
  同档取最高码率），base64url 编码后 `location.href` 到一个 `.invalid` 哨兵地址
- `resolver/browser/driver.rs`：建隐藏窗口、`on_navigation` 认出哨兵 → 回传 → 返回 `false`
  取消导航；隐藏等 12s 没拿到就**显形**让用户过验证码，再等 60s
- 通道用哨兵导航而不是 CDP：**不用新增 WebSocket 依赖**，也不用手写握手与帧编解码
- 载荷走 query 而非 fragment（`Url::query_pairs` 能直接解码），base64 用
  `URL_SAFE_NO_PAD` 避免 `+` `/` `=` 在 query 里被误处理

复用窗口时踩到两个真实缺陷，都已修：

1. **导航到同一 URL 不会重新加载文档**，抖音 SPA 也不会重新请求详情接口，第二次解析
   必然超时 → 每轮先导航到 `about:blank` 卸载旧文档，再加载目标页。
2. **`on_navigation` 闭包在窗口创建时就固定了**，直接持有某一轮的 sender 会让第二次
   解析的 receiver 立刻看到「通道已断开」，表现为 0.4 秒瞬间失败 → 改成每轮替换
   `Arc<Mutex<Option<Sender>>>` 槽位里的 sender。

安全：解析窗口**故意不进任何 capability**。`resolve_access`
（`tauri-2.11.5/src/ipc/authority.rs:439`）要求 origin 与 window 同时匹配，
我们的 capability 只有 `main` 且无 `remote`，所以抖音页面即使拿到
`__TAURI_INTERNALS__` 也调不动任何命令。窗口还用独立 `data_directory`
（`D:\VideoFlow\browser-resolver`），避免抖音 Cookie 写进主应用 profile。

### 21.3 M3U8 Parser

`resolver/m3u8.rs` 纯解析 + `resolver/hls.rs` Provider。`EXT-X-KEY`（AES-128）、
`EXT-X-BYTERANGE`、fMP4 的 `EXT-X-MAP` **不做处理，原样交给 FFmpeg**——
它原生支持（已实测本机 ffmpeg 有 `hls` demuxer 与 `crypto` 协议），
自己重写一遍只会引入偏差。

下载走新的 `EngineKind::Hls` → `media::hls_to_mp4`：tokio 起 ffmpeg，
`-progress pipe:1` 解析 `out_time_us`，用「已处理时长 / 总时长」摊出已下载字节。

一个必然踩到的坑：临时文件是 `.part` 结尾，**FFmpeg 推不出输出容器格式**，
报 `Unable to choose an output format`，必须显式 `-f mp4`。

## 22. 第十二轮：B 站账户登录解锁清晰度 + Browser 覆盖面扩展（2026-09-19）

并**确认功能真的有效**；抖音快手如需登录也一并做；
**Browser Resolver 覆盖面加入快手、推特（X）等主流平台**，作为「yt-dlp 解析不了时就用 Browser」的保险。

### 22.1 为什么登录能解锁清晰度（不是推测）

对 `BV1oZeA6fERD`（同时有 4K 与 1080P60）实测，无 Cookie 时 yt-dlp 明确输出：

```text
[BiliBili] Format(s) 4K 超高清, 1080P 60帧 are missing; you have to become a
premium member to download them. Use --cookies for the authentication
```

实际格式列表里最高只有 1920x1080@30fps（`30080`/`30077`/`100026`）。
这就是「登录解锁」这条路的依据：**服务端按 Cookie 决定下发哪些格式**。

一处必须说清的预期：登录只解决「需要登录」这一层，**1080P60 通常登录即可，
而 4K 与 1080P 高码率需要大会员**。所以设置页会查询并展示 `vipStatus`，
避免用户以为是程序没生效。

### 22.2 账户登录

- `account/mod.rs`（纯逻辑，可脱 GUI 单测）：站点表、`CookieRecord`、
  Netscape cookies.txt 的序列化与**按站点合并**（先删该站旧行再追加，
  多站点共用一个文件时互不覆盖）
- `account/window.rs`：独立登录窗口 `vf-account-login`，**与解析窗口共用
  `D:\VideoFlow\browser-resolver` profile** → 共享 WebView2 环境 → 共享 Cookie
  （依据：`tauri-runtime-wry/src/lib.rs:4793-4800` 按 `data_directory` 复用 WebContext）
- 新增来源前缀 `account:` → `--cookies D:\VideoFlow\cookies.txt`
- 5 个命令：`account_status` / `account_login` / `account_confirm_login` /
  `account_logout` / `account_refresh`

**httpOnly Cookie 怎么拿到**：B 站的 `SESSDATA` 是 httpOnly，JS 读不到，必须用
`WebviewWindow::cookies_for_url()`（文档明确包含 HTTP-only cookie；wry 逐项读
`IsHttpOnly`/`IsSecure`/`SameSite`/`Expires`，见 `wry-0.55.1/src/webview2/mod.rs:1520-1566`）。
它在 Windows 的同步命令或事件处理器里会死锁（wry#583），因此一律包在
`tauri::async_runtime::spawn_blocking` 里。

**登录态真的有效怎么确认**（两级客观证据）：

1. 用导出的 Cookie 调 `https://api.bilibili.com/x/web-interface/nav`，
   要求 `data.isLogin == true`，并取 `uname` 与 `vipStatus`(1=大会员)。
   服务端自己认可才算数，而不是我们自说自话。
2. 清晰度是否真解锁：对 `BV1oZeA6fERD` 跑 `yt-dlp -F`，看
   `1080P 60帧 are missing` 警告是否消失。

**一处自查发现的缺陷**：最初在校验**之前**就写了「已确认登录」标记，导致一次失败的
登录会留下「已登录」的假象。改成**校验通过才写标记**。

**抖音/快手不猜 Cookie 名**：这两个站点的登录 Cookie 名不稳定，`login_cookie: None`
表示不做自动判定，由用户点「我已完成登录」收工——比猜一个错的 Cookie 名更稳。

## 23. 第十三轮：用户反馈的三个问题（2026-09-20）

用户报了三件事：登录提示窗不自动消失、抖音未登录下载的视频无法播放、

### 23.1 控制台刷屏：所有事件推送一直失败（严重）

用户截图的控制台里刷满了：

```text
[videoflow] 推送事件 task.updated 失败：only alphanumeric, '-', '/', ':', '_'
permitted for event names: "task.updated"
```

**根因**：事件名用了 `.` 分隔（`task.updated` / `queue.updated` / `task.progress` /
`app.notice`），而 Tauri 的事件名校验只放行字母数字与 `-` `/` `:` `_`
（`tauri-2.11.5/src/event/event_name.rs:8-12`，校验失败返回 `IllegalEventName`）。
所以 `emit` **每次都直接失败、什么都不推送**——界面完全收不到实时更新。

为什么一直没被发现：界面里有一层 1 秒轮询对账（`App.tsx::useTaskReconcile`）
兜住了状态，所以看起来「只是进度条有点顿」，而失败日志被 `emit_event` 打了但没人看。
项目书 §4.2 当初就写的带点号事件名，实现照抄了，没意识到框架不允许。

**修复**：全部改为下划线命名，前后端同步：

| 旧 | 新 |
|---|---|
| `task.updated` | `task_updated` |
| `task.removed` | `task_removed` |
| `task.progress` | `task_progress` |
| `queue.updated` | `queue_updated` |

### 23.2 抖音视频「下载后无法播放」：是 H.265，不是文件损坏

用户下载的那条抖音 4K 视频打不开。逐项排查后确认**文件本身完全正常**：

| 检查 | 结果 |
|---|---|
| `ffprobe` 完整解码全片 | **退出码 0**，无任何报错 |
| MP4 结构 | `ftyp` → `moov`（偏移 36）→ `mdat`（偏移 89575），标准 faststart |
| 解码配置盒 | `hvcC` 存在且完整（213 字节） |
| 编码 | `hevc` / `hvc1`，3840x2160 **60fps** |
| 对照：能播的文件 | 全部是 `h264` / `avc1` |

**根因**：抖音的 4K 与 1440p 档**只提供 H.265**，而 Windows 自带播放器与不少播放器
解不了 H.265。实测该视频各档编码：

| 清晰度 | 编码 |
|---|---|
| 2160p | **hvc1（H.265）** |
| 1440p | **hvc1（H.265）** |
| 1080p | avc1（H.264） |
| 720p | avc1（H.264） |
| 576p | avc1（H.264） |

**注意：这与登录无关。** 用户以为是未登录导致，实际是编码兼容性——
4K 档在抖音侧就只有 H.265 一种编码可选。

**修复（两处）**：

1. **编码优先排序**：`hook.js::buildLadder` 原本在同分辨率里只挑**码率最高**的，
   于是 4K 档必然选中 H.265。改为**先比编码兼容性、再比码率**，
   规则与 yt-dlp 那条路（`ytdlp.rs::video_codec_rank`）完全一致：
   H.264 > H.265 > AV1 > VP9。
   这与之前 yt-dlp 路径修过的是**同一类 bug**（那次是「按体积升序导致选中 AV1」），
   Browser 路径当时漏改了。
2. **界面标出编码**：`QualityPicker` 的清晰度下拉现在显示
   「360P 25fps · H.264 · 8.9 MB」，用户选之前就能看到编码。
   `LadderEntry` 新增 `codec` 字段并透传到 `MediaStream.codec`（前端已有该字段）。

> 一个必须如实说明的取舍：**抖音 4K 仍然只有 H.265**，无法通过排序绕开——
> 该清晰度在服务端就只有这一种编码。想要 4K 就得能解 H.265（装 HEVC 扩展或换播放器）；
> 想要「双击就能播」就选 1080p 及以下（有 H.264）。

### 23.3 登录提示窗不自动消失

`SettingsPage::handleLogin` 的失败分支写了 `persistent: true`，于是提示条永不淡出。
但登录失败（尤其「已取消登录」只是用户主动关窗）属于低风险可重试操作，
不像文件损坏那样需要留在屏幕上复盘。改为 `persistent: false`（3.6 秒后自动消失）。

`handleLogout` 的失败分支保留 `persistent: true`——那是真实故障，值得留着。

### 24.1 一个范围判断（记录决策依据）

### 24.2 关键前提：容器与编码不是自由组合（全部实测）

捆绑的 `bin/ffmpeg.exe` 编码器与封装器齐备。但逐个**写入后完整解码**验证，
得到了真实可用矩阵——这是本次设计的核心约束：

| 容器 | 视频编码 | 音频编码 |
|---|---|---|
| mp4 / mkv | h264 / h265 / av1 / vp9 | aac / opus / mp3 / flac |
| webm | **仅 vp9 / av1** | **仅 opus** |
| mov | **仅 h264 / h265** | **仅 aac / mp3** |
| avi | h264 / av1 / vp9（**h265 排除**） | aac / mp3 / flac |
| flv | h264 / h265 / av1 / vp9 | aac / opus / mp3 / flac |

- **`avi` + H.265 写入成功、完整解码却报错，而 FFmpeg 不返回任何错误。**
  产出一个坏文件，只能靠黑名单拦。这与第 23 轮用户遇到的「下载后打不开」是**同一类问题**，
  绝不能在转换功能里重演。
- `webm`+H.264/AAC、`mov`+AV1/VP9/Opus/FLAC 会被 muxer 直接拒绝（写入即失败）。

### 24.6 自查中修掉的一个真实缺陷

`probe_streams` 最初按 `type,codec,width,height` 的顺序解析 ffprobe 的 csv 输出，
但 **`-of csv=p=0` 用的是 ffprobe 自己的字段顺序**，实测视频流是
`h264,video,1280,720`（编码在前），音频流更短（`aac,audio`）。结果**所有流信息都读成空**——
转换页的源文件回显与「有没有音轨」的拦截会一起失灵。

这是靠实测输出（`视频=None 音频=None`）发现的，不是靠读代码。修法是先定位类型字段、
再在其余字段里挑编码与宽高，并抽出 `parse_probe_line` 加了 3 项单测锁住格式。

### 24.7 已知限制

- **转码是纯软件编码**：AV1 与 H.265 较慢（实测 5 秒 720p 素材，VP9 37s、AV1 18s、H.265 16s，
  H.264 约 3s）。已用 `-threads` 按设备档位限流（性能档 2 / 平衡档 4 / 质量档不限），
  并支持随时暂停取消。未做硬件加速——`h264_nvenc` 等虽在，但本机是否可用未验证，
  贸然启用会引入一堆兼容分支。
- **暂停 = 重新开始**：FFmpeg 不支持转码断点续传，与 HLS 一致的既有取舍，界面文案已如实说明
  （「继续将从头开始」）。
- **转码质量参数不暴露**：用各编码器的合理默认 CRF，未加质量滑块。
- **转换任务并发固定为 1**：转码吃 CPU，本地文件又没有远端限流压力，
  放开并发跑多个 FFmpeg 会明显拖慢界面与下载。
- **历史只在解析成功时写入**：失败或粘错的链接不进历史，避免污染。

## 25. 第十五轮：玻璃错位修复 + GPU 加速 + 音频转换与音质提示（2026-09-20）

用户反馈五件事：

1. 导入视频后下方下拉框**位移**（向下移动后恢复），要修；
2. 下拉框 UI 要与整体一致（截图里左上角有多余弧线）；
3. 提示语「容器决定了能用的哪些编码」→「容器决定能用的编码」；
4. **有概率**出现位移更严重的情况（第二张截图，玻璃整块飘出去）；
5. 视频转换加 **GPU 辅助加速**（软件太慢）；再加**音频转换**（flac→mp3 等），
   并加质量提示——高质量转低质量可以，低质量转高质量要提示音质不会变好。

### 25.1 玻璃错位：根因是「按需渲染」漏了一次重绘

`GlassCanvas` 是**按需渲染**的（`needsRender` + rAF），面板位置只在重绘时才用
`getBoundingClientRect()` 读取。而它原本只监听两类变化：画布尺寸、以及面板自身的
**尺寸**变化（`ResizeObserver`）。于是「尺寸没变、位置变了」这一类就漏了：

- 转换页导入文件 → 文件列表插入 → 下方控件整体下移，**尺寸一个像素都没变**；
- 面板本身是 `overflow-y: auto` 的滚动容器 → 内容变高也不改变面板尺寸，
  `ResizeObserver` 更不会触发。

结果就是玻璃留在上一帧的位置上，直到下一次偶然的重绘（滚动、切页）才「恢复」——
与用户描述的「向下移动后恢复」「有概率」完全吻合。

修法是**两道网**（`GlassCanvas.tsx`）：

| 网 | 覆盖场景 | 代价 |
|---|---|---|
| `MutationObserver`（`childList + subtree`） | 列表插入、条件渲染、模式切换等**结构变化** | 只在结构变化时触发，几乎为零 |
| 低频矩形比对（空闲帧每 3 帧一次） | 文本换行、CSS 类切换等**结构没变但布局变了** | 每 3 帧读一次 `getBoundingClientRect` |

**刻意只监听 `childList`**：`attributes` 会被下载进度条改样式触发、`characterData`
会被进度文字触发，两样都会让画布在下载时每 250ms 白重绘一次。

### 25.2 实测验证（不是「看着差不多」）

用 CDP 在真实应用里注入布局变化，再对**截图做逐像素扫描**（列扫描找边缘），
把「玻璃画在哪」变成可对账的数字：

| 实验 | 期望落点（CSS y） | 扫描到的边界 | 结论 |
|---|---|---|---|
| 插入 DOM 块（结构变化） | 盒子 466..512 | **只**扫到 466.7 与 512.7 | 玻璃跟着走了，旧位置无残留 |
| 只改样式（结构没变） | 盒子 509..555 | **只**扫到 510 与 556 | 低频比对这道网单独也成立 |

两次都没有在旧位置（449 / 495）扫到任何边界——**残留玻璃为 0**。
另外确认了 448 那条线是 dropzone 的下边框（在两列之间的空隙列上同样存在），
不是残留玻璃。

### 25.3 GPU 硬件加速

**先探测再启用**，探测方式是**真的编一帧**，而不是看 `ffmpeg -encoders` 列表
（那只说明「编译进来了」）。本机实测的三种假阳性刚好证明了必要性：

| 编码器 | 列表里 | 实编结果 |
|---|---|---|
| `h264_qsv` / `hevc_qsv` | 有 | **成功** |
| `h264_nvenc` / `hevc_nvenc` | 有 | `Cannot load nvEncodeAPI64.dll`（驱动没给） |
| `av1_qsv` | 有 | `This version of runtime doesn't support AV1 encoding` |
| `vp9_qsv` | 有 | `Selected ratecontrol mode is unsupported` |

两个坑写在代码注释里，都是踩出来的：

- **探测素材要够大**：QSV 会以「当前分辨率不受支持」拒绝 16×16 这类过小的帧——
  那是素材的问题，会被误判成「硬件不可用」。改用 320×240 一帧。
- **QSV 只认 `-global_quality`，不认 `-crf`**：喂错不会报错，只是质量参数被静默忽略。

因此硬件路径只挂 **H.264 / H.265**（`h264_qsv` / `hevc_qsv`），AV1 与 VP9 没有硬件路径，
开关打开时自动回落软件编码。`ConvertPlan.use_hardware` 的语义是**「允许」**：
探测不通过就静默回落——宁可慢，也不能因为用户开了开关就产出编不出来的任务。
该字段 `#[serde(default)]` 为 false，**重启后恢复的旧任务仍按原来的软件路径跑**。

探测耗时约 1~2 秒（几乎全是 QSV 设备初始化），所以：两个编码器**并行**探测 +
进程内缓存一次 + **启动时后台预热**（`lib.rs`），用户打开转换页时不用等。

**端到端实测**（真实素材 1080p / 20s / 15 Mbps，走应用完整链路：任务 → 调度 → FFmpeg）：

| 路径 | 耗时 | 产物 | 完整解码 |
|---|---|---|---|
| 软件（`libx264 -crf 23`） | **43.7s** | 14.6 MB（5.74 Mbps） | 通过 |
| 硬件（`h264_qsv -global_quality 23`） | **9.7s** | 18.2 MB（7.17 Mbps） | 通过 |

**4.5 倍**。代价是文件大 25%（QSV 的 gq 23 比 x264 的 crf 23 更「舍得给码率」，
此前实测 PSNR 45.33 vs 44.71，画质并不更差）——这属于取舍，已如实写在这里。

界面侧：能力表下发 `hardwareAvailable` 与每个编码的 `hardware` 标记；
有硬件时开关默认打开，编码下拉标出「（GPU）」，下面写清会走哪条路；
任务卡的 `quality_label` 显示「H.264（GPU） · AAC」，用户看到的加速有据可查。

### 25.5 音质提示（提交前页内提示，不是事后弹窗）

规则（`src/features/convert/audioQuality.ts`，纯函数 + 11 项单测）：

| 源 → 目标 | 提示 |
|---|---|
| 无损 → 有损（FLAC → MP3） | **不提示**：这就是正常压缩 |
| 无损 → 无损（FLAC → WAV） | 说明：音质不变，只是换封装（WAV 体积会大很多） |
| 有损 → 无损（MP3 → FLAC） | **警告**：找不回丢掉的细节，文件还会变大 |
| 有损 → 有损且目标码率 ≥ 源 | **警告**：音质不会变好，只是不再继续损失 |

只在**音频转换模式**显示：视频转换时用户盯的是画面，音频码率那行只会变成噪音。

码率怎么读（实测两级回退，缺一不可）：

- 流级 `stream=bit_rate`：mp3 / aac 能读到（如 69188）；
- **纯音频文件的 flac 流级返回 `N/A`**，只能退到容器级 `format=bit_rate`（136193）——
  但容器级含全部轨道，所以**只在没有视频轨时才用它**兜底；
- 读不到就**不提示**：宁可不说，也不能拿编造的数字下结论
  （`parse_bitrate` 把 `N/A`、空串、0 一律当读不到，已加单测）。

## 26. 第十六轮：穿模修复 + 滚动条统一 + NVENC 实验性候选（2026-09-20）

用户反馈四件事：

2. 「图二的穿模 bug 还在」；

4. 图三图四那条**系统默认滚动条**要么删掉、要么做成透明并与整体 UI 一致，
   且**所有滚动位置风格统一**。

### 26.1 穿模的根因：画布不认祖先的裁剪区

前一轮我只修了「位置变了没重绘」，漏了另一件事：**画布不裁剪**。

面板本身是 `overflow: auto` 的滚动容器。里面的控件滚出可视区（或部分越界）时，
DOM 会被容器裁掉，但 `getBoundingClientRect()` 给的是**未裁剪**的矩形，
于是玻璃整块画到面板外面 —— 压在相邻面板上就是「穿模」，
在面板边缘留下半截玻璃就是「多出来的那条线」。

实测证据（转换页导入一个文件后，第二行下拉框正好压在面板底边上）：

| 项 | 数值（CSS y） |
|---|---|
| 面板可视区 | 96 ~ **630** |
| 音频编码下拉框 DOM 矩形 | 597 ~ **642**（被面板裁掉 12px） |
| 修复前像素扫描 | 598.7（顶边）、631.3（面板底）、**644.7（越界玻璃的底边）**、651.3（下一个面板顶边） |
| 修复后像素扫描 | 598.7、631.3、651.3 —— **644.7 消失** |

修法（`GlassCanvas.tsx`）：给每个面板求「祖先里所有会裁剪的容器的交集」，
scissor 用这个交集，而 `uRect` 仍传面板真实矩形 —— **只裁像素，不改形状、
折射与倒角**。祖先矩形在一次重绘内缓存，避免重复 `getComputedStyle`。

### 26.2 滚动条：全局统一，且踩了 Chromium 的一个坑

两件事：

- **坑**：Chromium 里一旦设置了标准属性 `scrollbar-width` / `scrollbar-color`，
  `::-webkit-scrollbar` 那套会被**整体忽略**。旧 `.vf-scroll` 两套都写了，
  实际生效的是标准属性那套。
- **漏网**：工作台面板、背景页、历史下拉只写了 `overflow-y: auto`，没带 `.vf-scroll`，
  于是露出系统默认的白色滚动条（带上下箭头）——就是用户截图里那条。

改法：滚动条外观改为**全局规则**（`::-webkit-scrollbar` 8px、透明轨道、
半透明白色圆角滑块、悬停变亮、**箭头按钮不显示**），`.vf-scroll` 只保留溢出行为。
新增的滚动容器不会再漏。

实测：面板 `offsetWidth - clientWidth` 由 **16 → 8**（16 就是系统默认宽度），
下载队列的 `.vf-scroll` 容器同样是 8，风格一致。

### 26.3 NVENC：实验性候选，参数独立，失败只回落不崩

**候选列表化**：`VideoCodecSpec.hardware` 从「单个」改成**按优先级排列的候选数组**，
每条候选自带自己的质量参数：

| 编码 | 候选（优先级从上到下） | 质量参数 |
|---|---|---|
| H.264 | `h264_qsv`（已验证）→ `h264_nvenc`（实验性） | `-global_quality 23` / `-rc vbr -cq 23 -b:v 0` |
| H.265 | `hevc_qsv`（已验证）→ `hevc_nvenc`（实验性） | `-global_quality 28` / `-rc vbr -cq 28 -b:v 0` |

参数**各自独立**，绝不互相套用（QSV 不认 `-cq`，NVENC 不认 `-global_quality`，
喂错都不报错、只会静默忽略）——单测直接锁死「编码器后面紧跟的参数串必须等于
这条路径自己的参数」。

**三道回落**（对应「不允许崩毁」）：

1. 探测阶段：某条候选失败/线程 panic 只等于「这一条不可用」，取下一个候选；
   全部落空 → 软件编码；
2. 转码阶段：硬件路径真的编不动时（驱动抽风、分辨率不被支持、实验性参数被拒），
   **自动改用软件参数重跑一次**——暂停/取消是用户的意思，绝不重试；
3. 界面：实验性路径标注「NVENC · 实验性」，任务卡写「H.264（GPU·QSV）」。

**修期间抓到的一个真 bug（并行探测的假阴性）**：加 NVENC 候选后我把探测改成
并行（4 个 ffmpeg 同时起），结果启动日志变成 `["h265:QSV"]` ——
`h264_qsv` 被误判成不可用。同一条命令在 shell 里单独跑、两个并行跑都成功，
说明是多会话同时初始化硬件时的干扰。改为**串行探测 + 某编码拿到可用路径就停止**
（后面的候选本来也用不上），并加了「首次失败隔 600ms 再试一次」兜住开机瞬间的 GPU 忙碌。
修复后启动日志恢复为 `["h264:QSV", "h265:QSV"]`。

### 27.1 滚动条：可以隐藏，做成了「滚动时显形、停下 1 秒隐去」

这一路踩了三个坑，都写进了 `base.css` 的注释：

| 坑 | 现象 | 结论 |
|---|---|---|
| 两套属性同时写 | `::-webkit-scrollbar` 完全不生效 | Chromium 一旦有 `scrollbar-width`/`scrollbar-color`，就**整体忽略** webkit 那套 |
| 只写 webkit 那套 | 面板预留了 8px 宽度，屏幕上**什么都画不出来**（连 `!important` 强制上色也不显示） | 本机 WebView2 里 webkit 滚动条**只占位、不绘制** |
| 靠 `*:hover` 显形 | 悬停在面板上滑块仍不出现 | 滚动条由合成器绘制，悬停宿主元素**不会**让它重绘 |

最终方案：**标准属性**（`scrollbar-width: thin` + `scrollbar-color`）打底，
由 `AppShell` 里的一段监听给正在滚动的容器打 `vf-scrolling` 类来显形。

实测（面板右侧滚动条那一列的平均亮度）：

| 状态 | 亮度 | 结论 |
|---|---|---|
| 静息 | 106 75 114 119 134 110 82 82 80 | 滑块透明 = **看不见** |
| 滚动进行中 | 106 88 124 127 141 119 94 94 92 | 滑块显形（整列 +6~12） |
| 停下约 2 秒后 | 与静息**逐像素相同** | 自动隐去 |

顺带解决了「滚动条一出现就挤压内容宽度」的老问题：`thin` 宽度是**常驻**的，
显隐只改颜色，**不触发重排**。

### 27.4 补充：那条线最终定为「背景图内容」，不是 UI

   | | 边界屏幕 y（css） |

## 28. 第十八轮：v1.0.0 安装包（setup.exe）（2026-09-20）

用户要求：**按程序打包制作 v1.0 版本的 `setup.exe`**。

### 28.1 打包必须补的一件事：sidecar 根本没打进包

原来的 `tauri.conf.json` 只有 `targets: ["nsis"]`，**没有 `resources`**——
`bin/ffmpeg.exe`、`ffprobe.exe`、`yt-dlp.exe`（合计 213 MB）在开发机上靠
`sidecar::locate()` 的「源码树 / 当前目录」候选路径找到，**装完就没有了**：
一个没有 FFmpeg 的下载/转换器等于不可用。

补法（目标路径刻意与查找顺序对齐）：

```json
"resources": {
  "../bin/ffmpeg.exe":  "bin/ffmpeg.exe",
  "../bin/ffprobe.exe": "bin/ffprobe.exe",
  "../bin/yt-dlp.exe":  "bin/yt-dlp.exe"
}
```

`sidecar::locate()` 的第一候选就是「exe 同级的 `bin/`」，所以资源落在
`<安装目录>\bin\` 正好命中，**无需改一行代码**。

### 28.2 踩到的坑：`bundle.nsis` 在 v2 里不合法

第一次构建直接报：

```
Error `"tauri.conf.json"` error on `bundle`: Additional properties are not allowed ('nsis' was unexpected)
```

Tauri v2 把平台相关配置收进了 `bundle.windows`：正确写法是
`bundle.windows.nsis`（`installMode: currentUser` + `languages: ["SimpChinese"]`）。

### 28.3 构建与实测

| 项 | 结果 |
|---|---|
| 版本号 | `tauri.conf.json` / `Cargo.toml` / `package.json` 统一为 **1.0.0** |
| 构建 | `tauri build -- --jobs 1`（release）：依赖编译 **35m18s**，NSIS 工具链自动下载（nsis-3.11 + nsis_tauri_utils） |
| 产物 | `VideoFlow_1.0.0_x64-setup.exe` **74.7 MB**（体积几乎全由三个 sidecar 的压缩包决定） |
| 静默安装 | `setup.exe /S` → 退出码 0，装到 `%LOCALAPPDATA%\VideoFlow`（currentUser，**不需要管理员**） |
| 安装内容 | `videoflow.exe` 28.5 MB、`bin\ffmpeg.exe` 98.1 MB、`bin\ffprobe.exe` 97.9 MB、`bin\yt-dlp.exe` 17.0 MB、`uninstall.exe` |
| **装完能否自给自足** | 已安装实例自报：ffmpeg = `…\VideoFlow\bin\ffmpeg.exe`、yt-dlp = `…\VideoFlow\bin\yt-dlp.exe`（**都在安装目录内**，不再依赖源码树） |
| 硬件探测 | `["h264:QSV", "h265:QSV"]`，能力表 4 条编码器路径 |
| **真实转码** | 已安装的 release 版跑 1080p/20s 素材：**12.7s 完成**，任务卡 `H.264（GPU·QSV） · AAC`，产物完整解码通过 |

产物已放到项目根目录：`VideoFlow_1.0.0_x64-setup.exe`；同时把根目录的
`VideoFlow.exe` 从 debug 快照换成 **release 构建**（28.5 MB，性能也更好）。

### 28.4 已知约束（如实记录）

- **安装位置是 `%LOCALAPPDATA%\VideoFlow`**（currentUser 模式）：不需要管理员，
  但也就不会出现在「所有用户」的 Program Files 里。
- **应用数据仍在 `D:\VideoFlow`**（`settings.json` / `tasks.json` / `history.json` /
  `Downloads` 都是硬编码路径，见 `storage`/`history` 模块）：这是既有设计（「全部落在 D 盘」），
  但**目标机器必须有 D 盘**，否则配置与下载会失败——换机器部署时要先确认这一点。
- **WebView2 运行时**：用 Tauri 默认策略（缺失时 installer 联网下载 bootstrapper）。
  目标机器若已装 WebView2（Win10 21H2+/Win11 自带）则不会触发下载。

## 29. 第十九轮：Liquid Glass 档的「横向/纵向亮线」（2026-09-20）

用户反馈：**切到 Liquid Glass（WebGL）档后界面出现明显的横向/纵向亮线，CSS 毛玻璃档没有**；
要求只修光学层，**不要动布局、尺寸、间距、组件位置**。

### 29.1 定位（先量化，再动手）

写了一个「亮脊检测」：对截图逐行判断「整行是否显著亮于上下邻行（Δ≥10 且覆盖率≥35%）」，
在**同一页面、同一滚动位置**下对两档各跑一次：

| 档位 | 检出的水平亮线（css y） |
|---|---|
| Liquid Glass（质量档） | 97.3, **180.7**, **388**, 450.7, 540, 651.3 |
| CSS 毛玻璃（性能档） | 97.3, 840.7（只有面板自身的边） |

再把检出位置与 DOM 逐一对照（导出面板内所有子元素的 rect）：

| 亮线位置 | 对应元素 |
|---|---|
| 180.7 / 388 | **投放框 `.vf-convert__dropzone` 的上下虚线描边**（x 范围 292.7~1210 与它的 24px 圆角完全吻合） |
| 450.7 / 540 | 两个下拉控件的边缘 |
| 97.3 / 651.3 | 面板自身边缘 |

强度：投放框虚线在 Liquid Glass 档平均 **Δ+27（最亮处 +46）**，CSS 档 ≈ 0（几乎不可见）。

### 29.2 根因（两条，都在光学层）

1. **着色器少了 CSS 档那层「玻璃填充」抬底。**
   CSS 档在背景之上还叠了一层 `--vf-glass-fill`（半透明白）；Liquid Glass 档只把背景
   按 `uBgOpacity`（用户设为 0.48）向 `uBgBase`（暗蓝）混合，**底部因此比 CSS 档暗约 20 级**
   —— 叠在上面的细白描边对比被放大，就成了「亮线」。着色器注释里本来就写着
   「保持与 CSS 档位的观感一致」，但这一层没做。
2. **Liquid Glass 档的 DOM 描边与着色器光边重叠成「双边缘」。**
   `.vf-glass-host[data-glass-mode="webgl"]` 只清了 `background` / `box-shadow`，
   **没清 `border`**：`.vf-select` 等自带的 1px 描边会和着色器画出的倒角高光叠成双线
   （此前看到的「控件四角多一条弧」就是这个）；另外 `::before` 那层 inset 高光
   （原本是「着色器不可用时兜底」）在着色器可用时也是重复的一层。

### 29.3 修法（全部只改光学层，几何零改动）

1. `glassShader.ts`：在背景混合之后补上与 CSS 档一致的 **12% 白抬底**；
2. `glass.css`：Liquid Glass 档的玻璃宿主 **不留 DOM 描边**（光边完全交给着色器）；
3. 删掉重复的 `::before` inset 高光；
4. 装饰性细白线（投放框虚线、次级按钮、分隔线）在这一档压淡（26% → 13% / 12%）。

### 29.4 实测

| 指标（投放框虚线那一行） | 修复前 | 修复后 |
|---|---|---|
| 亮脊覆盖 | 471 / 690 | 407 / 690 |
| 平均对比度 Δ | **+27**（最亮 +46） | **+12** |

对比度降约 55%：虚线作为「可投放区域」的提示仍看得见，但不再成为刺眼的亮线；
控制件边缘的双线（双弧）也随 DOM 描边一并消失。

### 29.5 待确认

用户还提到「图三问题按退出键无法退出」——是**关闭按钮点了没反应**，还是**按 Esc 键期望退出/关闭弹层**？
两种的排查方向不同，已在回复里请用户确认（本轮未改动任何退出相关代码）。

## 30. 第二十轮：窗口按钮与拖动全部失效（权限缺失）（2026-09-20）

用户反馈（紧接着上一轮的 release 包）：**关闭没反应、最小化没反应、最大化没反应、窗口也拖不动**——
四个症状指向同一个环节：它们全都走 Tauri 的窗口插件命令。

### 30.1 根因：`core:default` 不含「会改变窗口状态」的命令

`src-tauri/capabilities/default.json` 里原本只有：

```json
"permissions": ["core:default", "dialog:default", "dialog:allow-open"]
```

Tauri 2 的 `core:default` **只放开只读的窗口 API**（读取尺寸/位置之类）。
标题栏三个按钮与拖动区域用的是：

| 界面动作 | 实际命令 | 需要的能力 |
|---|---|---|
| 关闭 | `plugin:window\|close` | `core:window:allow-close` |
| 最小化 | `plugin:window\|minimize` | `core:window:allow-minimize` |
| 最大化/还原 | `plugin:window\|toggle_maximize` | `core:window:allow-toggle-maximize` |
| 判断是否已最大化 | `plugin:window\|is_maximized` | `core:window:allow-is-maximized` |
| 拖动窗口（`data-tauri-drag-region`） | `plugin:window\|start_dragging` | `core:window:allow-start-dragging` |

这些都没授权 → 调用被拒；而前端的 `guard(...)` 把错误吞掉了，于是「点了没反应」，
错误也不出现在界面上——**这正是这个 bug 能一直活着的原因**。

### 30.2 修法与实测

`capabilities/default.json` 补上上表五个权限（外加 `maximize` / `unmaximize` 两条对称项）。

实测（新构建的实例，通过 CDP 直接调这些命令）：

| 命令 | 结果 |
|---|---|
| `is_maximized` | `OK:false` |
| `minimize` | `OK` |
| `toggle_maximize` | `OK` |
| `unmaximize` | `OK` |
| `close` | 调用后**进程直接退出**（连 CDP 回包都来不及发）✓ |

### 30.3 反思（记下来）

- 前两轮的 release 冒烟测试只验了**业务链路**（能力表、硬件探测、真实转码），
  **没验窗口控制**——所以「能跑业务」掩盖了「窗口按钮全废」。
  已安装版的验收清单里应固定加上「关闭/最小化/最大化/拖动」四项。
- `guard()` 吞错误是必要的（Tauri 之外预览时不该报错），但**调试期应该把它记一条
  `console.error`**，否则权限这类问题在界面上完全无声——后续考虑加上（本轮未改）。
